# MFMS Phase 2 — Data Integrity & Firestore Cost Sprints

**Marble Factory Management System (MFMS)**
**Document version:** 1.0
**Date:** August 2026
**Status:** Planning document (post–Phase 1 / parallel to v1.1)
**Sprints:** S36–S41

## 1. Purpose

This document plans the remediation of **four defects** found in the Firestore data
layer audit. Two are silent data-corruption bugs; two are the cause of the
**daily free-tier quota being exceeded**.

Related documents:

- [`MFMS_v1.1_Roadmap.md`](./MFMS_v1.1_Roadmap.md) — feature backlog (S25–S30)
- [`MFMS_Phase1_Identity_Onboarding_Sprints.md`](./MFMS_Phase1_Identity_Onboarding_Sprints.md) — identity (S31–S35)
- **This file:** data integrity + read/write cost (S36–S41)

This phase adds **no new features**. Every sprint either prevents data corruption
or reduces document reads/writes.

## 2. Baseline defects

| # | Defect | Type | Quota impact |
|---|--------|------|--------------|
| **D1** | Stock read-modify-write without atomicity (`rawMaterials`, `finishedGoods`, `productionBatches`) | Correctness | None |
| **D2** | Sequence numbers generated by counting whole collection (16 sites) | Correctness **+ cost** | High (write path) |
| **D3** | Dashboard: 17 unbounded `snapshots()` listeners, no date window, re-attached per entry | Cost | **Critical** |
| **D4** | `syncCustomerBalance` downloads all factory sales orders + loads to sync one customer; write amplification per payment | Cost | High |

### D1 detail

`raw_material_repository.dart:135-194` reads `currentStock`, computes
`newStock` in Dart, writes the absolute value in a `WriteBatch`. The batch makes
the writes atomic but the read is outside it — concurrent movements overwrite
each other. `stockTransactions` rows are still written, so the ledger and the
stock level permanently disagree. `averageCost` corrupts the same way, which
propagates into `stockValue` → material cost → `netProfit`.

### D2 detail

16 functions use `.get()` on the collection and `docs.length + 1`. Three failure
modes: (a) concurrent creates produce duplicate numbers; (b) **deleting** a
document makes the next create *reuse* a live number — no concurrency needed, and
`customer_repository` cascade-deletes across 11 collections; (c) O(n) reads per
create, growing forever. Creating one job-work order triggers 4 full-collection
scans (order + load + invoice + collection numbers).

### D3 detail

`dashboard_bloc.dart:191-350` attaches 17 listeners, all
`where('factoryId', ...)` with no `limit()` and no date filter.
`_onWatchStarted` calls `_cancelSubscriptions()` then re-attaches all 17, so every
dashboard entry re-reads all history. Only 9 `limit()` calls exist in the whole
codebase.

**Key finding:** `DashboardFinancePeriod` (daily…allTime) already exists, but the
range is applied **client-side** via
`dashboard_cashflow_metrics.dart:68 contains(date, start, end)` — after download.
The window never reaches the query. This makes S39 a smaller change than expected.

### D4 detail

`customer_ledger_service.dart:54-76` calls
`watchSalesOrders(factoryId).first` and `watchLoads(factoryId).first`. Two
problems: it is factory-scoped for a single-customer calculation, and `.first`
on a `snapshots()` stream opens a listener, takes one event, discards it — no
cache reuse, full billed read every call.

Write amplification per job-work payment: 4 writes in the transaction, then
`_syncInvoiceFromPayments` rewrites invoice+load+order (3), then
`refreshContainerFromLoads` rewrites every load and load-invoice plus grand
invoice (2N+1), then `syncCustomerBalance` writes the customer (1). On a 5-load
order ≈ **19 writes for one payment** against a 20,000/day ceiling.

## 4. Architecture decisions (locked for Phase 2)

| # | Decision | Rationale |
|---|----------|-----------|
| A1 | Prefer `FieldValue.increment` over `runTransaction` for stock | `increment` is atomic **and works offline**; `runTransaction` requires a server round trip and would break factory-floor recording |
| A2 | Store `totalQuantity` + `totalValue`; derive `averageCost = totalValue / totalQuantity` | Makes weighted-average cost expressible as two increments, so no read is needed and the result is exact under concurrency |
| A3 | Sequence counters never decrement on delete | Gaps are normal and auditable; duplicates destroy the audit trail |
| A4 | Push the existing `DashboardFinancePeriod` into the Firestore query | Range abstraction already exists; only the query layer changes |
| A5 | No backend migration; stay on Firestore | Repository layer already isolates data access if that changes later |
| A6 | Every sprint ships a measured before/after read count | Prevents "fixed it" without evidence |

(213 existing + 13 new).

| `Tooltip` (reset / collapse icons) | `No Overlay widget found` when expanding, then two misleading `RenderFlex overflowed` errors caused by the substituted `ErrorWidget` | `Semantics(button: true, label: ...)` |

The overflow errors were symptoms, not separate bugs — worth remembering when
reading a stack of layout errors after one build failure.
`test/presentation/widgets/debug/firestore_metrics_overlay_test.dart` now mounts
the overlay through `MaterialApp.builder` exactly as `app.dart` does, so any
future Overlay-dependent widget fails in CI rather than on device.

**How read tracking works.** `trackedCollection(firestore, name)` returns a
`TrackedCollectionReference` in debug builds and the raw reference in release,
so there is no production overhead. Because `TrackedQuery.where()` /
`.orderBy()` / `.limit()` re-wrap, tracking survives the whole chain and only
the collection getters needed changing — 24 files instead of ~450 call sites.

Counting mirrors Firestore billing: a `get()` bills `docs.length`, and a
`snapshots()` listener bills every document in its first snapshot then only
`docChanges.length` on later snapshots.

**Two SDK constraints worth knowing.**

1. `Query` and `CollectionReference` are annotated `@sealed`, so the wrapper
   carries a file-level `ignore: subtype_of_sealed_class` (the same approach
   `fake_cloud_firestore` uses). A `cloud_firestore` upgrade that adds a member
   will break this one file at compile time — a loud, contained failure.
2. `Transaction.set` and `WriteBatch.set` type-check their argument against the
   SDK's private reference classes and throw on a wrapper. So
   `TrackedCollectionReference.doc()` deliberately returns the **real**
   `DocumentReference`. Batches and transactions are therefore untouched and
   safe.

**Known tracking gaps** (all deliberate, none affect the quota diagnosis):

| Surface | Tracked? | Why |
|---------|----------|-----|
| Query reads via repository collection getters | **Yes** | Covers all 17 dashboard listeners and every `watch*`/`fetch*` |
| Single-document reads (`.doc(id).get()` / `.snapshots()`) | No | `doc()` must return a real reference; these are 1 document each |
| Writes inside `WriteBatch` / `runTransaction` | No | Real references bypass the wrapper; count from the Emulator UI or add explicit `recordWrites` on the paths under test |
| `add()` on a tracked collection | **Yes** | Counted as one write |
| Inline multi-line `_firestore.collection('x').where(...)` chains | No | ~20 sites in `job_work_*`, `customer_repository`, `payment_repository`; S40 converts these while fixing D4 |
| `auth_repository` | No | Document-level only, negligible volume |

Because `syncCustomerBalance` goes through `watchSalesOrders` and `watchLoads`,
the D4 amplifier **is** measurable today.

**Emulator default.** Debug builds now use the emulator suite automatically.
Opt back into production with `--dart-define=USE_PROD_FIREBASE=true`; the legacy
`USE_FIREBASE_EMULATORS=true` flag still works. Release builds always use
production, and the startup log states which target is active.

**Seeder.** `bin/seed_data.dart` gained `--emulator` and `--emulator-host`
instead of a new script. `_parseArgs` also had to be fixed — it silently dropped
bare flags, so `--emulator` would have been ignored.

### How to test on device

1. Start the emulators on the PC:
   ```
   firebase emulators:start --import=./.emulator-data --export-on-exit
   ```
2. Seed a working dataset into the emulator:
   ```
   dart run bin/seed_data.dart --emulator
   ```
   For a physical device, the seeder still runs on the PC, so `localhost` is
   correct here. Confirm the banner prints `Target : EMULATOR (localhost)`.
3. Run the app. On the **Android emulator** no flags are needed — debug builds
   now default to the emulator suite on `10.0.2.2`:
   ```
   flutter run
   ```
   On a **physical device** (phone or tablet), neither default host works.
   Prefer adb port reversal — it tunnels over the USB connection already used
   by `flutter run`, so there is no IP to look up and no firewall to open:
   ```
   adb reverse tcp:8080 tcp:8080
   adb reverse tcp:9099 tcp:9099
   adb reverse tcp:5001 tcp:5001
   flutter run --dart-define=EMULATOR_HOST=localhost
   ```
   Re-run the `adb reverse` commands after unplugging the device or restarting
   adb; they do not survive a disconnect.

   As a fallback, use the PC's LAN IP with both devices on the same Wi-Fi
   (`ipconfig` → IPv4) and allow inbound traffic on those ports in Windows
   Firewall:
   ```
   flutter run --dart-define=EMULATOR_HOST=192.168.1.10
   ```
4. Confirm the console prints
   `Firebase emulators: host=... (auth:9099, firestore:8080, functions:5001)`.
   If it prints `using PRODUCTION project` instead, stop — something is
   overriding the default.
5. Open `http://localhost:4000` on the PC. Your device's writes must appear in
   the Emulator UI and **not** in the Firebase Console.
6. **Quota proof:** open Firebase Console → Firestore → Usage and note the read
   count. Do 10 minutes of app work on the device, including several hot
   restarts, then refresh. The count must be unchanged.
7. **Verify the overlay:** a black `R … W … L …` pill appears at the top-left
   (drag to reposition, tap to expand the per-collection breakdown, refresh icon
   to reset). Cold-start the app, tap reset, open the dashboard, and record the
   numbers in §12.
8. **Sanity-check the instrumentation itself:** with the dashboard open, expect
   ~17 listener attaches (`L`) across the collections listed in D3. If `L` is
   far lower, a repository is bypassing `trackedCollection`.
9. **Regression check:** confirm production is still reachable when asked for:
   ```
   flutter run --dart-define=USE_PROD_FIREBASE=true
   ```
   Log in with a real account, confirm data loads, then go back to the emulator.

## 7. Sprint S37 — Sequence counters — **DONE**

**Goal:** unique, monotonic document numbers at O(1) cost.

### Data model

```
counters/{factoryId}__{sequenceKey}
  factoryId: string
  sequenceKey: string      // 'jobWorkInvoice', 'salesOrder', 'stockIn', ...
  year: number
  value: number            // last allocated
  updatedAt: timestamp
```

### Tasks

| # | Task | Description | Acceptance criteria |
|---|------|-------------|---------------------|
| 37.1 | `SequenceNumberService` | `allocate({factoryId, key, prefix, year})` — `runTransaction` reads counter, writes `value + 1`, returns formatted number | Returns `JWI-2026-0041`; never returns a value twice |
| 37.2 | Seed migration | For each sequence key, scan the collection **once** and set the counter to the current maximum parsed number | Existing documents keep their numbers; next create continues the sequence |
| 37.3 | Migrate 16 call sites | Replace every `_generate*Number` / `generateAgreementNumber` body with a service call | Zero `docs.length + 1` patterns remain in `lib/data/repositories/` |
| 37.4 | Year rollover | On year change, reset `value` to 0 and update `year` inside the same transaction | First document of a new year is `-0001` |
| 37.5 | Offline fallback | Allocation needs connectivity; on failure surface a clear retryable error rather than a timestamp-derived fake (removes the `expense_repository.dart:307` millis fallback) | Offline create shows "number allocation needs connection", no duplicate risk |
| 37.6 | Rules | `counters/{id}` readable/writable only by same-factory authenticated users; `value` may only increase | Rules test: decrement rejected |
| 37.7 | Tests | Unit: format, rollover, monotonicity. Integration: 20 parallel allocations yield 20 distinct numbers | All pass |

### What shipped, and where it differs from the plan

**Seeding is on-demand, not startup-only (37.2).** A startup-only migration leaves
a race: a user who creates a job-work order before the migration finishes gets
`JW-2026-0001` on top of an existing series. So `allocate()` seeds itself — if the
counter document is absent it scans that one collection, sets the counter to the
highest number already issued, and retries. `SequenceSeedMigration` still runs at
login, but it is now only a pre-warm: correctness no longer depends on it having
run. The scan happens at most once per sequence per factory, because the first
allocation creates the counter.

**21 sequences, 17 generator functions.** The plan said "16 call sites". The real
count is 17 `_generate*Number` functions mapping to 21 counters, because
`stockTransactions` and `inventoryTransactions` each hold several series
distinguished by `movementType`. Two of those functions share one counter:
`production_repository._generateStockOutNumber` and
`raw_material_repository._generateTransactionNumber(stockOut)` both write the
`STK-OUT` series, so they must not have separate counters.

**Sequence metadata lives on the enum.** `DocumentSequence` carries the prefix,
the collection, the field holding the number, and the optional `movementType`
filter. The seed scan is driven off that, so adding a sequence is one enum entry
rather than an entry plus a migration table.

**No index changes were needed.** The seed scan filters on `factoryId` plus
`movementType`, both equality — Firestore serves that by merging single-field
indexes, so `firestore.indexes.json` is untouched.

**Rules enforce forward-only (37.6).** Within a year a counter update must
strictly increase `value`; a new year may reset it. `SequenceNumberService.seed`
also refuses to move a counter backwards client-side, so a stale seed run cannot
rewind a live series.

**Removed the expense fallback (37.5).** `expense_repository` used to catch any
failure and mint `EXP-<year>-<millis>`, which collides with the real series.
Allocation failures now propagate as `SequenceNumberException`, which carries
`isRetryable` and an offline-specific message.

**Not migrated: `SalesAgreementRepository.nextOrderSequence`.** It is `max + 1`
over one agreement's orders, not `count + 1` over a collection — bounded in cost
and not a document number, so it is out of scope here. It is still racy under
concurrent order creation on the same agreement; worth a per-agreement counter
later if duplicate `orderSequence` values ever show up.

7. **Offline behaviour:** turn on airplane mode and try to create an expense. It
   must fail with "Cannot create a new EXP number while offline", *not* succeed
   with a timestamp-derived number. Reconnect and confirm the create works.

No duplicate document numbers under concurrency or after deletion; create cost is
flat.

## 8. Sprint S38 — Stock atomicity

**Goal:** concurrent stock movements cannot lose an update, **without losing
offline recording**.

### Data model change

`rawMaterials/{id}` and `finishedGoods/{id}` gain:

```
totalQuantity: number     // replaces currentStock as source of truth
totalValue:    number     // Σ (qty × unitCost) received
```

`currentStock` / `currentQuantity` and `averageCost` become **derived**:
`averageCost = totalQuantity > 0 ? totalValue / totalQuantity : 0`.
Both legacy fields are kept in sync during a deprecation window (A2, §4).

Stock-in becomes two atomic transforms and **no read**:

```
increment(totalQuantity, +quantity)
increment(totalValue,    +quantity * unitCost)
```

### Tasks

| # | Task | Description | Acceptance criteria |
|---|------|-------------|---------------------|
| 38.1 | Entity + model update | Add `totalQuantity`/`totalValue` to `RawMaterial`, `FinishedGood`; make `averageCost`, `stockValue`, `isLowStock` derived getters | `flutter analyze` clean; existing UI unchanged |
| 38.2 | Backfill migration | For every material/good, set `totalQuantity = currentStock`, `totalValue = currentStock * averageCost` | Post-migration `averageCost` matches pre-migration for every document |
| 38.3 | `recordStockIn` / `recordStockOut` | Replace read-compute-batch with `increment` + transaction doc in one `WriteBatch` | No `getMaterialByType` call before the write |
| 38.4 | Finished goods receipt & adjustment | Same conversion for `finished_goods_repository.dart:191`, `:300` | Per-SKU increments, no pre-read |
| 38.5 | Production batch path | `production_repository.dart:132`, `:273` — material consumption and the delta on update become increments | Batch create touches 5 collections with no stale reads |
| 38.6 | Negative-stock guard | Client pre-check kept for UX; authoritative guard added in `firestore.rules` comparing incoming vs existing | Rules test: write driving `totalQuantity` below 0 rejected |
| 38.7 | Reconciliation report | Debug screen comparing `totalQuantity` against the sum of `stockTransactions` per material | Any drift is visible and attributable |
| 38.8 | Tests | Unit: derived average cost, negative guard. Integration: 10 parallel stock-ins land exactly | All pass |

### Deliverables

- `lib/domain/entities/raw_material.dart`, `finished_good.dart` (modified)
- `lib/data/models/raw_material_model.dart`, `finished_good_model.dart` (modified)
- `raw_material_repository.dart`, `finished_goods_repository.dart`, `production_repository.dart` (modified)
- `lib/data/services/stock_backfill_migration.dart` (new)
- `lib/presentation/screens/debug/stock_reconciliation_screen.dart` (new)
- `firestore.rules` (modified)
- `test/data/repositories/stock_atomicity_test.dart` (new)

### How to test on device

1. **Reproduce the bug first, on the emulator.** Two phones, same material.
   Phone A records stock-in of 50 tons, Phone B records 30 tons — tap Save
   simultaneously. Before the fix: final stock is 130 or 150, not 180, while
   **both** `stockTransactions` rows exist. Screenshot this; it is the proof the
   fix is needed.
2. **Verify the fix.** Repeat step 1 after the change. Final `totalQuantity` must
   be exactly 180, and `averageCost` must equal
   `(50×costA + 30×costB) / 80`. Check in the Emulator UI.
3. **Offline recording (this is the point of A1).** Put the phone in airplane
   mode, record a stock-in, confirm the UI updates immediately from the local
   cache. Re-enable network and confirm the value lands on the server. This must
   pass — if it fails, the increment approach was not applied correctly.
4. **Offline concurrency.** Phone A offline records +50; Phone B online records
   +30; bring A back online. Final must be +80, not +50 or +30. This is the case
   `runTransaction` cannot handle and is the main reason for A1.
5. **Negative stock.** Try to record stock-out larger than available. Expect a
   clear client error; then verify via a direct Emulator UI write attempt that the
   rule also rejects it server-side.
6. **Migration safety.** Export the emulator dataset, run the backfill, and use
   the reconciliation screen to confirm every material's `averageCost` and
   `stockValue` are unchanged. **Do not run against production until this passes.**
7. **Production batch.** Create a batch consuming raw material and producing
   graded slabs; confirm raw stock down, finished goods up, and both transaction
   rows written, with the P&L material cost unchanged.

### Exit

Stock is atomic, offline recording still works, and existing valuations are
provably unchanged by the migration.

## 9. Sprint S39 — Dashboard windowing

**Goal:** dashboard read cost proportional to the selected period, not to total
history. This is the sprint that fixes the quota.

### Tasks

| # | Task | Description | Acceptance criteria |
|---|------|-------------|---------------------|
| 39.1 | Range reaches the query | Add `{DateTime? from, DateTime? to}` to the `watch*` methods the dashboard uses; apply `where(dateField, >=, from)` | Query-level filter replaces `contains(date, start, end)` post-filtering |

| 39.8 | Tests | Bloc tests: period change triggers new subscription; widget tests still pass | All pass |

2. **After the change,** repeat with period = Daily. Reads should be a small
   fraction of the baseline. Record both numbers in §12.
3. **Period switching.** Cycle Daily → Weekly → Monthly → Yearly and watch the
   overlay. Each switch should add reads proportional to the window; Daily must be
   far cheaper than Yearly. If they cost the same, the filter is still client-side.
4. **Re-entry cost (36.6 regression).** Navigate Dashboard → Job Work → Dashboard
   five times. Additional reads should be near zero. Before the fix this was 5×
   full re-read.
5. **Correctness, not just cheapness.** For one period, compare every dashboard
   KPI against the pre-change build on the same dataset — revenue, receivables,
   dispatch, stock-cut. Numbers must match exactly. A cheaper but wrong dashboard
   is a worse outcome than an expensive one.
6. **Index errors.** Exercise all six periods and watch logcat
   (`flutter logs`) for `failed-precondition`. Deploy indexes with
   `firebase deploy --only firestore:indexes` and re-test.
7. **Real-device quota check.** Point a debug build at a **staging** Firebase
   project, use the app normally for an hour, and compare Console reads against
   the same exercise on the old build.

### Exit

Dashboard cold open and re-entry are bounded and measured; all KPIs unchanged.

## 14. Risks & mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| S38 backfill corrupts valuations | **Critical** | Export first; reconciliation screen; emulator dry run on imported production copy |
| Derived `averageCost` changes historical reports | High | Keep legacy fields written during deprecation window; compare P&L before/after |
| Sequence seed set too low → duplicate numbers | High | Seed from parsed maximum, not count; verify per key before release |
| Dashboard windowing changes KPI values | High | Task 39.5 requires exact KPI match against the old build before merge |
| Removing `_syncInvoiceFromPayments` hides a real repair path | Medium | Make it conditional, not deleted; keep a manual "recompute" action |
| Missing composite index crashes a period | Medium | Exercise all six periods in QA; deploy indexes before app release |
| Offline behaviour regresses | High | Airplane-mode test is a release gate for S38 |
